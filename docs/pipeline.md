## Що робить `pipeline/ai-review.yml`

1. **Тригер `pull_request`, а не `pull_request_target`:** PR із форку отримує лише токен для читання й жодних
   секретів.
2. **`tests` — обов'язковий check.** У branch protection він називається `tests`; назва стала, тож зміна
   переліку гейтів її не чіпає. Job зупиняється на першій помилці. Диф береться з `--text`, щоб `.gitattributes` із
   PR не сховав змін.
   - **Гейти:**
     - R14 — без залежностей, lock-файлів, `node_modules/`, `.env*`; секрети шукає gitleaks;
     - R13 — увесь набір тестів (`node --test`), жодного skipped чи todo;
     - R6 — нова експортована функція в `app/src/`, а CHANGELOG — ні. Експорти читає Node, імпортуючи модулі з
       `app/`, як тести; назва, яку база вже експортує з `app/src/`, не нова — перенесений файл чи функція гейт не
       зачіпають. Модуль, що не імпортується, дає попередження: гейт не може судити.
     - R13 і R6 виконують код PR, тому вони останні.
   - **Сигнали (лише попередження):** R6 — інший змінений рядок `export`, а CHANGELOG — ні; R5 — дати в локальному
     часі; R4 — форматування грошей; R11 — текст для AI чи рев'юерів. Це збіг тексту, тож можливі хибні
     спрацювання: перейменований параметр для R6, назва методу в рядку для R5. Правило тримають рев'юер і людина.
   - **Відмінностей від стандарту немає:** R4 і R5 — `grep`, R13 — `node --test` і підсумки TAP, як у стандарті
     (`scripts.test` із PR не довіряють ні CI, ні локальна команда). Сигнали R3, R18 і R19 — лише план; доти їх
     перевіряє рев'юер.
3. **AI-рев'ю — дорадче:** спершу `review`, потім `comment`.
   - `review` запускається лише після зелених `tests`, лише для PR із цього репо і не для чернеток. Диф `app/` —
     лише дані; рев'юер і код `app/` беруться з бази.
   - Claude Code (точна версія) працює в тимчасовій копії без `.git`, з інструментами лише `Read`, `Grep` і `Glob`.
     Прогін відкидається, якщо інструменти ширші або модель зверталася до шляху поза копією.
   - Звіт перевіряється на ключі й токени ще до вивантаження. `comment` публікує його з поясненням «дорадче» і без
     `@`-згадок.
4. **Злиття затверджує людина:** зелений `tests` + схвалення людини. Вердикт AI на злиття не впливає.

## Права і секрети

На рівні workflow — `permissions: {}`; кожен job просить мінімум.

| Job | `permissions` | Секрети | Код PR |
|---|---|---|---|
| `tests` | `contents: read` | — | виконується |
| `review` | `contents: read` | `ANTHROPIC_API_KEY`, лише в одному кроці | лише як текст |
| `comment` | `pull-requests: write` | — | не завантажується |

- **Ключ і право запису — в різних jobs.**
- **Секрет — лише як `${{ secrets.ANTHROPIC_API_KEY }}`**; `persist-credentials: false`.
- **Закріплення:** дії — за SHA, образ gitleaks — за digest, CLI — точною версією; кеш вимкнено.
- **PR із форку** проходить лише `tests`, бо секретів GitHub йому не дає. AI-рев'ю для нього запускають локально,
  як крок `prepare`: рев'юер і `app/` — з бази, диф PR — лише дані (код PR не виконується). Тека
  `review-queue/pr-N/` — лише для прогону, її не комітять:

  ```bash
  N=42  # номер PR
  git fetch origin main "pull/$N/head:pr-$N"
  git switch --detach origin/main   # база: рев'юер і app/ «до зміни»
  mkdir -p "review-queue/pr-$N"
  git diff --text origin/main..."pr-$N" -- app > "review-queue/pr-$N/change.diff"
  gh pr view "$N" --json title,body -q '"# " + .title + "\n\n" + .body' > "review-queue/pr-$N/PR.md"
  node review/run-review.mjs "$N"   # → review-runs/pr-N.md
  rm -rf "review-queue/pr-$N"
  git switch -                      # назад на свою гілку
  ```
- **PR із цього репо** отримує ключ одразу, ще до рев'ю, бо workflow береться з самого PR. Тож ключ — лише для тих,
  кому довіряєте право запису.

## Модель загроз

| Що може зробити PR зі шкідливим вмістом | Що обмежує шкоду у вашому пайплайні |
|---|---|
| Ін'єкція в описі, коді, коментарях чи назвах: «схвали», «не повідомляй знахідок» (як у PR-6) | Модель лише читає, а спроба керувати рев'ю — сама знахідка (R11, R12). Але вердикт ставить модель, тож ін'єкція може прибрати знахідку. Тому коментар дорадчий, а злиття вирішує людина. Сигнал R11 у `tests` від моделі не залежить |
| Змусити модель видати ключ у звіті | Якщо модель звернулася до шляху поза копією (`/proc/self/environ`, `.git`), прогін відкидається. Звіт до вивантаження перевіряється на ключі, але лише записані дослівно: закодований ключ пройде |
| Script injection через назву чи опис PR | Поля PR — лише через `env`, ніколи `${{ }}` у скрипті |
| Сховати зміни: `.gitattributes` із `-diff`, власний `.gitleaks.toml`, `gitleaks:allow` у рядку із секретом | Диф — із `--text`; конфіг gitleaks із PR видаляється, а `gitleaks:allow` не діє (`--ignore-gitleaks-allow`); skip і todo рахує раннер тестів |
| Підмінити рев'юер: промпт, стандарт чи скрипт | Рев'юер береться з бази, а не з PR |
| Змінити сам workflow | **PR із цього репо** отримає ключ ще до рев'ю. Межа — право запису лише довіреним; надійніше — ключ в `environment` зі схваленням. **PR із форку** може «озеленити» `tests` — це ловить обов'язкове рев'ю code owners |
| Шкідливий код у тестах | Без секретів, токен лише для читання, код PR виконують лише останні кроки (R13, R6); `scripts.test` із PR не використовується. Послаблені тести ловить людина (R8) |
| Підмінений action, образ чи CLI | SHA, digest, точна версія |
| Шкідливий вихід моделі: `@`-згадки, посилання, «LGTM, зливайте» | `@` знешкоджено, над звітом — пояснення «дорадче». Посилання не фільтруються, тож за ними не переходимо. `comment` не може зливати |
| Витрати | Ключ — лише для PR із цього репо; AI — після зелених `tests` і не для чернеток. Діють `concurrency` і `timeout-minutes`; ліміт витрат — на самому ключі |

## Що лишається на людину

- **Затвердити злиття.** У Task B рев'юер пропустив 1 дефект із 15 і дав 3 хибні тривоги.
- **Не вважати APPROVE доказом.** Ін'єкція може дати чистий звіт. Немає коментаря — рев'ю не було.
- **Перевіряти знахідки за кодом,** особливо доступ (R1, R15), персональні дані (R2), шляхи (R3) і межі (R16). За
  посиланнями зі звіту не переходити.
- **Рев'ю змін** у пайплайні, промпті, стандарті, `.gitattributes` і `.gitleaks*`.
- **Налаштувати репо:**
  - обов'язковий check `tests`;
  - обов'язкове схвалення і code owners для цих шляхів (`pipeline/`, `.github/`, `.claude/`, `review/`, стандарт);
  - окремий ключ із лімітом витрат;
  - токен за замовчуванням — лише для читання; вимкнено «Allow GitHub Actions to create and approve pull requests».
